---
name: estimate-food
description: Estimate foods, edible weight and nutrition from photos attached or pasted in ChatGPT, image URLs or image data using the MyFitnessPal estimator; optionally log a user-requested meal.
---

Use `estimate_food_from_attachment` for a photo attached or pasted into ChatGPT. Its `openai/fileParams` metadata lets the host supply `image` as `{download_url, file_id, mime_type?, file_name?}`. Use the actual attached file reference; do not invent URLs, file IDs or base64. Do not ask the user to publish a photo when the host can supply the reference. For an existing HTTPS image URL or actual base64 image data, use `estimate_food_from_image` instead.

Pass food identity, preparation, known dimensions/reference objects, and added fats in `context` when available. Pass `measured_weight_g` only for a measured TOTAL edible weight; it overrides visual weight. A measurement of just one component must not be assigned to the entire plate. Preserve raw/cooked state and measured-versus-estimated provenance. Ask targeted questions when identity, preparation or hidden oil materially changes the result.

When estimating just chicken, fish, steak or salad on a mixed plate, set `food_focus` to the requested component; mass and nutrients then refer only to that food. If a component's weight is measured, set that focus and supply its measured grams. `plate_diameter_cm` must be an actual user-measured OUTER rim diameter, never a guessed standard plate. `additional_images` accepts up to two more attached views of the SAME portion through fileParams; a side view can reveal thickness. The URL tool supports equivalent `additional_image_urls`. Do not sum portions across views.

Return the food description, mass estimate and range, calories/macros, assumptions and relevant questions. The range is subjective and uncalibrated. Model nutrition is not a verified MyFitnessPal entry. The response's `accuracy_target.status` explicitly distinguishes supplied measured weight from an unproven estimate. Photo-only chicken estimation has NOT met a 20% per-portion target on separate test cases. If the user requires that bound, ask for a scale weight; a measured reference or another view helps geometry but does not guarantee it. Do not present a narrow model range, a development median below 20%, or an assumed standard portion as proof of accuracy. Do not log an uncertain estimate while claiming the user's 20% requirement was satisfied. No fine-tuned weights or historical learning were deployed. The estimator sends the photo to OpenAI using the server key and never writes the diary.

For “estimate this,” stop after estimation. For “log this,” continue the [logging workflow](../manage-myfitnesspal/SKILL.md), using measured grams when available. Search and inspect a matching food entry; do not substitute model-generated nutrient values while claiming a verified database match. Do not create a custom food unless that is the user's intended change.

If attachment resolution fails, report that the photo was not analyzed and ask the user to reattach it with this app selected. A bare attachment ID or sandbox path cannot be resolved by the server. Expired URLs require a fresh host reference. Never include signed download URLs in the user-facing result. Tool/schema discovery is available through `get_myfitnesspal_tool_guide`; if absent, refresh or reconnect the connector rather than falling back silently to the URL tool.

Distinguish attachment transport from inference: `ATTACHMENT_DOWNLOAD_FAILED` reports download/decode reason and HTTP status without invoking vision. `attachment_transport.downloaded_bytes` and `vision_input=inline_image_bytes` confirm the image was fetched and sent inline. `ESTIMATION_API_FAILED` at `image_inference` reports sanitized upstream_code, upstream_param and request_id; an HTTP 400 alone is not proof of URL expiration. Report diagnostic_id for troubleshooting. Do not ask for another upload to fix schema, billing or model configuration errors.
